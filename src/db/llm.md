# src/db/

## Purpose

The database layer: the Drizzle schema, the Postgres client, and (by pointer) the SQL migrations in
`/drizzle`. It exists because payments are the first thing in this project that must be remembered
between requests — a link staff created on Monday has to still be payable on Wednesday, and a payment
must be recorded exactly once. Delete it and the payment-link builder goes back to fabricating URLs.
Since D105b it also holds the catalogue: products, their specs, images and vendor sources.

## Owns

- [`schema.ts`](schema.ts) — three tables (`payment_links`, `payment_attempts`, `payment_events`), five
  enums, one sequence. Every money invariant is a CHECK or a unique index here, not an `if` in a feature.
- [`catalog-schema.ts`](catalog-schema.ts) — the catalogue (D105b): `products`, `tire_specs`,
  `wheel_specs`, `accessory_specs`, `product_images`, `product_sources`, five enums. Re-exported from
  `schema.ts`, which stays the one module `drizzle.config.ts` and `client.ts` read.
- [`client.ts`](client.ts) — `getDb()`: lazy `pg` pool + Drizzle, `attachDatabasePool` for Fluid Compute.
  Connect within 5 s, each query within 8 s (`query_timeout`, client-side), and a client released with
  a query still running is ended, never pooled again (D145 audit, BE-RESILIENCE; D151).
- `/drizzle/*.sql` (repo root) — generated by `npm run db:generate`, except
  `0001_payment_events_append_only.sql`, which is hand-written (the append-only trigger).

## Rules

- **Payment money is integer cents.** Never `numeric`, never a float, never a formatted string in a column.
  **`products.price` is the one exception (D105b):** `numeric(10,2)`, nullable, and deliberately without a
  currency, tax or unit. Owner, 2026-09-30: *"lets not give the price column a meaning, price is just
  price"*. It is a display number, never an amount charged; a payment link's amount is typed by staff
  (D92) and never read from it.
- **`products.brand` is empty only on an accessory** (D125), made true by `products_brand_required`.
  **`products.extra_specs`** is a jsonb array of `{label, value}` pairs for vendor facts too sparse for
  a column; a fact most rows carry gets a column instead (owner, 2026-10-03).
- **`products.part_number` and `tire_specs.mud_snow` (D142, migration `0005`)** hold two facts that
  were extra specs. A part number is a wheel's or accessory's vendor code, at most 70 characters
  (`products_part_number_length`); a tire never has one (`products_part_number_not_tire`). `mud_snow` is
  the M+S marking, `false` for both "no" and "not stated", the shape of `winter_approved`. `0005` moved
  the values itself and left `slug` and `updated_at` alone.
- **`products_search_trgm_idx` (D173, migration `0006`; rebuilt by `0009`, D193, over brand, model and
  name only, the part number being the vendor's SKU)** is a GIN trigram index over
  `productSearchText()`, defined beside `products` in `catalog-schema.ts`. `0006` also creates the `pg_trgm`
  extension (hand-added above drizzle-kit's output; drizzle-kit does not manage extensions). The search
  query filters on the same function, so the index and the query cannot spell the expression two ways.
- **A spec row's category is pinned by the database.** Each spec table carries a `category` column with a
  CHECK and a composite foreign key to `products (id, category)`. Don't drop either half.
- **A uniqueness that a foreign key points at is a table `unique()`, not a `uniqueIndex()`.** drizzle-kit
  emits indexes after foreign keys, so the index form generates a migration that fails
  (`products_id_category_key`, found by applying `0002` to a real Postgres).
- **`products.sku` is written by the database (D192, migration `0008`).** `products_fill_sku` (BEFORE
  INSERT) draws `PW-` + category letter + six random digits when an insert leaves it out, and
  `products_keep_sku` refuses any change. The schema's `$defaultFn` sends `DEFAULT`, so no insert names
  the column. `0008` is hand-written past drizzle-kit's output (function, backfill, triggers).
- **Invariants live in the database.** If a rule can be a CHECK, unique index or trigger, it is one.
  Application code may check it too, for a friendly error — the database is what makes it true.
- **Migrations are append-only.** Never edit a migration that has run anywhere; add a new one.
  `npm run db:check` must pass.
- **Migrations use `DATABASE_URL_UNPOOLED`; the app uses `DATABASE_URL`** (pooled). DDL must not go
  through PgBouncer.
- **Migrations run in the Vercel build** (`scripts/db-migrate.mjs`, first step of `npm run build`). Both
  Neon URLs are Sensitive and cannot be pulled locally, so there is no manual production migrate step.
  Migrations must be backward-compatible with the code already live: the build migrates, then deploys.
- **`payment_events` is append-only** — enforced by trigger. Corrections are new events.
- Full design and reasoning: [`docs/payments.md`](../../docs/payments.md). Pointers, not copies.

## Connects to

- **Depends on:** `drizzle-orm`, `pg`, `@vercel/functions`; env vars `DATABASE_URL`,

- **Depended on by:** `src/features/payments/service.ts` (every read and write; D99–D108), and through it
  the admin and `/pay`; `src/features/catalog/` (`rows.ts`, `queries.ts`, `store.ts`; D105b).

## Don't

- Don't import `client.ts` from a client component — it opens TCP connections.
- Don't pass `statement_timeout`, `lock_timeout` or `options` to the pool, or `SET` them per session:
  Neon's pooled endpoint refuses unknown startup parameters (every connection fails), and a session
  `SET` leaks across PgBouncer clients, the import scripts included. Server-side limits go in as
  `SET LOCAL` inside the transaction that needs them (D145 audit; D151).
- Don't use Neon's HTTP driver for payment writes: it cannot hold the `SELECT … FOR UPDATE` transaction
  the attempt flow needs.
- Don't store card numbers, CVV, or anything but brand and last four.
- Don't delete a `payment_links` row. Cancel it. The foreign keys will refuse anyway.
- Don't add stock, MAP or MSRP columns to the catalogue, or a finish enum (D105b). Vendor cost was
  ruled out too, until **D125** put each vendor's own price on its `product_sources.vendor_price` row:
  staff only, and no storefront query may select it (`src/features/catalog/queries.ts` header).
